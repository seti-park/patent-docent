# T24 — 출구 검사는 디스크 재독본 위에서 돈다 (`read.source-digest` 가 실물이 된다)

## §1 무엇이 문제였나 (sol 지적 1 뒷절반 · opus max 판정과의 충돌)

`read.source-digest` 는 **명세가 신고한 원천 지문**과 **검사에 넘어온 원천 문자열의 지문**을
대조한다(`reader/lib/source_digest.py`). 그런데 엔진은 진입 때 파일을 **한 번** 읽어 메모리에
들고(`engine/stages/read.py:1433-1434`), 그 문자열로 명세의 지문을 적고, **같은 문자열**을
출구 검사에 넘긴다(`:1712-1719`). **자기가 적은 값을 자기가 확인한다** — 이 자리에서 이 검사는
항진명제이고 실패할 수 없다.

계약의 행은 *"원천이 도중에 바뀐 런은 폐기 대상이다"* 라며 `halt` 를 정한다. sol 은 *"근거가
거짓이다(여기서 실패하면 코드 결함이다)"* 라 했고 opus max 는 *"계약이 halt 를 정했다"* 고
했다. 인계문서의 세 안(ⓐ 문언 교체 · ⓑ escalate · ⓒ 이연)은 **셋 다 항진명제를 받아들인 채**
처분과 문언만 손본다.

## §2 T24 — 채택 (ⓓ)

### ⒜ 결정

**출구 판정점의 검사 직전에 원천 파일을 디스크에서 다시 읽어, 그 재독본을 출구 검사의
`CheckContext.source_text` 로 넘긴다.** 재시도 루프의 **매 회차**마다 다시 읽는다.

그러면 비교가 **「명세에 찍힌 지문(진입 시점)」 ↔ 「디스크의 지문(출구 시점)」** 이 되어,
런 도중 파일이 바뀌면 **실제로 잡힌다.**

| 항목 | 값 |
|---|---|
| 계약 문언 | **무접촉** — *"원천이 도중에 바뀐 런은 폐기 대상"* 이 고칠 필요 없이 **참이 된다** |
| 처분 | **`halt` 그대로** |
| `_failure_verdict` 의 분기 위치 | **그대로**(원장 §3 이 동결한 자리를 건드리지 않는다) |
| 진단 출력 | 파일 경로 · 기대(명세의 `patent.source_digest`) · 실측(재독본 지문) |
| `reader/lib` | **한 줄도 바뀌지 않는다** — 바뀌는 것은 엔진이 검사에 **무엇을 넘기느냐** 하나다 |
| 조기 판정점 | **메모리 사본 유지** — 거기엔 지문 검사가 없어 재독하면 파일 변경이 「분해 결함」으로 오진된다 |

### ⒝ 사유

- **두 감사를 실물로 살린다.** opus max 의 판정(계약이 halt 를 정했다)은 그대로 서고, sol 의
  판정(근거가 거짓이다)은 **근거를 참으로 만들어** 해소된다. ⓐ 도 둘을 살리지만 **문서를
  고쳐서** 살리고 ⓓ 는 **실물을 고쳐서** 살린다.
- 진입의 `read.input-digest` 와 출구의 `read.source-digest` 가 런의 앞뒤를 **괄호처럼 감싼다.**
  지금은 진입 이후부터 출구까지 파일이 바뀌면 아무 검사도 모른다 — 레인 왕복이 분 단위라
  이 창은 실제로 열려 있다.
- 재정 P-U2(원천이 바뀌었으면 부분 복구가 아니라 새 런)와 일치한다.

### ⒞ 채택과 함께 받아들인 비용

- 파일 읽기 + 해시 1회 × 출구 회차 — 무시할 수준.
- **★ 런 도중 원문 파일을 열어 저장하면 런이 무효가 된다.** 편집기의 자동 포맷도 포함된다.
  이것은 계약이 원래 약속한 보호를 **처음으로 실제로 하는 것**이지만, 운영상 불편할 수 있어
  메모에 고지되었고 그대로 채택되었다.
- 검사가 진짜로 실패할 수 있게 되므로 **T25 가 중요해진다** — 진짜 halt 가 나야 할 자리에
  재시도가 한 번 붙으면 레인 한 왕복을 버린다.

# T25 — halt 행(재시도 없음)의 검사가 실패하면 출구 루프를 즉시 나온다

## §1 무엇이 문제였나 (sol 지적 1 앞절반 · 원장 §3 미결 1행)

계약의 `read.source-digest` 행은 `action: halt` 단독(`retry(n)` 없음)이다. 그런데 출구 판정점
`retry_budget.points[id=exit]` 는 `checks: checks_before_exit` **전체**에 `max_retries: 1`

재시도한다. **재시도 없는 halt 가 실제로는 레인 한 왕복을 더 돌린다.** `points_binding`
규칙은 `retry(n)` 이 적힌 행만 보므로 이것을 잡지 못한다.

## §2 T25 — 채택 (ⓙ)

### ⒜ 결정

없이 즉시 나온다.** 판정은 그 행의 `halt` 다.

**두 단계로 집행한다.** 라운드 A 에서 **최소판**(위 한 문장을 코드로) — 라운드 B 의 T26

선언하고 러너는 그 부분집합만 재시도한다).

### ⒝ 사유

**무효인 런을 한 번 더 돌릴 이유가 없다.** T24 와 짝이 맞는다 — T24 가 이 검사를 진짜로

# T27 — 지적의 처분에 자리를 만든다 (처분 원장 + 관문)

## §1 무엇이 문제였나 (B-2)

감수 원문은 `docs/lessons/` 에 전문 보존되고 재정은 `docs/decisions/` 에 가는데, **「지적 N →
처분(수용/부분/기각/이연) + 사유 + 포인터」를 한 행씩 적는 자리가 없다.** 실제 처분 기록이
커밋 메시지(`c3fe549`)에 있었다 — 검색이 안 되고 고칠 수도 없는 곳이다. ROUTING §5 ⑼ 가
*「처분 없이 사라진 지적은 없어야 한다」* 고 정했는데 이 리포에는 그것을 강제하는 기계가 없다.

**실제로 둘이 빠졌다.** ⑴ sol 지적 1 의 앞절반(halt 행 재시도)이 원장에 오르지 않아 인계문서가
「할 일은 하나」로 틀렸다(`7c8ce3c` 에서 정정). ⑵ sol 지적 4 의 뒷절반 — *"`verify_declared_inputs`
가 훗날 fail 행을 반환하게 리팩터되면 halt 가 조용히 escalate 로 바뀐다, 함수 단위 방어가
없다"* — 는 앞절반(진입 갈래에 실재함 확인)만 처분되고 **사유 없이 사라졌다.**
