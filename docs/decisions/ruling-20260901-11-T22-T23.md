# T22 — 레인 로그 검사 2종에 전용 실패 행을 신설한다

## §0 Owner 육성 (원문)

> **`전용 행 + escalate, 재시도 없음 (추천)`**

**좌표** = `session_011sBzix6vtfqZryjyGYhcat`. 총괄이 배경·문제·선택지 3안을 서술한 뒤의 회신.

## §1 무엇이 문제였나 (sol 감사 지적 2)

`read.lane-log-shape` 와 `read.lane-log-digest-value` 는 **레인 왕복 기록**을 검사한다 —
전자는 로그의 **형태**, 후자는 로그에 실린 **지문 값**. 이 둘이 있어야 *"이 런이 실제로
무엇을 읽었는가"* 를 사후에 증명할 수 있다(재정 P-12 의 핵심).

**그런데 계약의 `failure:` 표에 이 둘의 행이 없다.** 실패하면 코드가 **무관한 `read.verbatim`
행**의 처분(`retry(1)` → `escalate`)을 그대로 빌려 쓴다.

**실측**(총괄 직접 재현):
```
_failure_verdict(c, [CheckRow("read.lane-log-shape")],        repeated=False) → ('escalate', None)
_failure_verdict(c, [CheckRow("read.lane-log-digest-value")], repeated=False) → ('escalate', None)
```

**★ 어긋남이 둘이다.**

**⑴ 계약이 이 검사들에 대해 그렇게 말한 적이 없다.** `read.verbatim` 행의 조건문에 두 검사는
없다. **코드가 지어낸 처분**이며, 이것이 이번 라운드가 A-2/A-3·Y-3 으로 벌한 계열이다.

**⑵ 빌려온 `retry(1)` 이 실제로는 0회다.** 두 검사는 출구 재시도 루프가 **완전히 끝난 뒤**
결과 목록에 합류한다(`engine/stages/read.py` — 루프 종료 후 `rows = [entry_row, *rows,
check_lane_log_shape(...), check_lane_log_digest_value(...)]`). 실패해도 재시도할 기회가
이미 지나갔다. **빌려 쓰는 처분의 절반이 허구다.**

## §2 T22 — 채택

### ⒜ 결정

**두 검사에 전용 실패 행을 신설한다.**

| 항목 | 값 |
|---|---|
| `action` | **`escalate`** |
| `retry(n)` | **적지 않는다** |
| `points` | **없음** — 어느 판정점에도 속하지 않는다 |
| `note` | 두 검사가 **재시도 루프 밖에서 합류**한다는 사실을 명기한다 |

### ⒝ ★ `retry(n)` 을 적지 않는 것이 이 재정의 핵심이다

**적으면 오늘 0회인 재시도를 계약이 다시 허구로 선언한다.** 그것이 정확히 §1 ⑵ 가 벌하는
형태이며, 이 재정이 그 형태를 고치면서 같은 형태를 새로 만들면 아무것도 고치지 않은 것이다.

**계약은 실제로 일어나는 일만 적는다.**

### ⒞ `halt` 를 고르지 않은 사유

**`halt` 도 논거가 있다** — 왕복 기록이 깨졌다는 것은 *"이 런이 무엇을 읽었는지 증명할 수
없다"* 는 뜻이고, 증명 못 하는 런을 버리는 것은 `read.source-digest` 와 같은 격이다.

**그러나 고르지 않았다.** 레인 로그 결함이 **재시도로 회복 가능한지가 아직 실측되지 않았다.**
`halt` 는 되돌릴 수 없는 처분이고, **근거 없이 되돌릴 수 없는 쪽을 고르지 않는다.**
회복 가능성 실측은 백로그 **B-1**(디스크 로그 사후 변조 미탐지)이 같은 자리를 건드리므로
**그때 함께 재는 편이 싸다** — 그 실측 뒤에 `halt` 로 올릴 여지는 열려 있다.

### ⒟ 기각 — `read.verbatim` 행의 조건문에 두 검사를 추가

**최소 변경이지만 틀렸다.** 그 행은 `retry(1)` 인데 두 검사는 루프 밖이라 0회다.
**선언과 실물의 어긋남을 새로 만드는 것**이며 §1 ⑵ 를 고치는 대신 성문화한다.

### ⒠ 성질 — 규율 11 의 정규 선상신 처분

**실패표에 행을 신설하는 것은 검사의 판정 공간을 정한다.** 총괄 재량이 아니다.
다만 **채택안은 오늘의 실동작을 성문화**하므로 **소급 문제가 없다** — 지금 `escalate` 로
가던 것이 계속 `escalate` 로 간다. 바뀌는 것은 **그 처분의 출처**다(빌려온 행 → 자기 행).

# T23 — 미분류 목록에 실행 귀속을 신설한다

## §0 Owner 육성 (원문)

> **`reported_by 배열을 넣는다 (추천)`**

## §1 무엇이 문제였나 (opus max 감사 Y-6)

READ 는 같은 특허를 **두 번 독립으로** 읽는다(`read-a`·`read-b`). `unclassified_dependents`
목록은 두 실행의 신고를 **합집합**으로 만든다(재정 T18 계열 처분).

**두 실행이 같은 청구항을 두고 다른 문언을 신고하면 두 행이 서는데, 어느 행이 어느 실행
것인지 목록이 말하지 않는다.**

**이 목록은 CP1 표면에 렌더된다** — Owner 가 승인 전에 읽는 화면이다. 같은 청구항이 두 번
뜨는데 왜 두 번인지가 적혀 있지 않다.

**실측** — `convergence.schema.json` 은 `unclassified_dependents.items` 와 **최상위 객체
양쪽 다** `additionalProperties: false` 다. 따라서 **행 단위 귀속 필드도 최상위 고지 필드도**
스키마 변경 없이는 넣을 수 없다. 감사 발주가 물은 *"고지 문구만 판정서 서식에 넣을 수
있는가"* 의 답은 **불가**다.

## §2 T23 — 채택

### ⒜ 결정

**`unclassified_dependents.items` 에 `reported_by` 를 신설한다.**

```
"reported_by": {"type": "array",
                "items": {"enum": ["read-a", "read-b"]},
                "minItems": 1, "uniqueItems": true}
```

`required` 에 넣는다.

### ⒝ 사유

**dedupe 동일성 축을 건드리지 않는다.** 지금 같은 신고는 `(claim, dependency_type, text)`
3튜플로 접히는데, `reported_by` 는 그 **접힘의 결과에 이름표를 붙일 뿐** 접는 기준을 바꾸지
않는다. 두 실행이 같은 신고를 냈으면 **한 행에 둘 다** 들어가고, 갈렸으면 **두 행이 서되
각자 누구인지** 적힌다.

**두 행이 선 이유가 목록 자체에서 읽힌다** — 지금은 렌더 고지를 읽어야 안다.

### ⒞ 기각 2건

| 안 | 기각 사유 |
|---|---|
| **`canonical: true\|false`** | 더 작지만 **두 실행이 같은 신고를 냈을 때 표현이 애매하다** — 한 행인가 두 행인가, `true` 인가. 애매한 표현은 다음 사람이 저마다 해석한다 |
| **렌더 고지만**(이번 라운드 재량 집행분) | **기계가 읽는 JSON 만 보는 하류는 여전히 모른다.** 지금은 하류가 없으나 `design`·`compose` 가 서면 생긴다. 그때 고치는 것이 지금보다 비싸다 |

**★ 렌더 고지는 지운다.** T23 이 목록 자체에 귀속을 넣으므로 *"귀속을 말하지 못한다"* 는
고지는 **거짓이 된다.** 남기면 이번 라운드가 벌한 「낡은 문언」 계열이 된다.

### ⒟ 성질 — 규율 11 의 정규 선상신 처분

**판정서 서식의 값 공간 + 키 추가(스키마 변경).** 재정 T21 이 같은 `items` 에 `text_status`
를 신설한 것과 **정확히 같은 격**이다.

**경계(재정 N8)** — `contracts/schemas/` 이므로 **프로젝트 간 계약이 아니다**
(historian 상신 불요 · `reader_version` 무관).

### ⒠ ★ 소급하지 않는다 — 행위시법

**`runs/**` 의 기존 3런은 `reported_by` 를 들지 않으며 그대로 선다.** 렌더는 키 부재를
방어해 구 판을 그대로 그린다(재정 T21 이 `text_status` 에 쓴 것과 같은 형태 · P-U1).
