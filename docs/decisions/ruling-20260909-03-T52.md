## 무엇이 이 재정을 부른 실측인가

16차 저작이 **바꾸지 않은 원본**에서 반례를 얻었고 총괄이 독립 재현했다(추기 83).
`read_closed` 가 읽기 업무 오류 `E1` 을 잡는데, `remember` 가 **그 오류를 담을 결과 객체를 만드는 호출**에서
자원 실패가 나면 `step` 이 값을 돌려주지 못하고 그대로 던진다. 그러면 결과 슬롯에 **앞 단계의 `open` 성공이 남고**,
`finally` 가 그것을 업무 결과로 확정하며, `seal` 이 미완료 단계의 성공 봉인을 거부해 `TransitionError` 를 낸다.
**반환은 `E1` 도 `E2` 도 아니고, `business` 는 Success 이며, `failures` 에 `E1` 이 없다.**

이 의무는 **12차부터 열려 있었다** — `R13-PROOF-OBLIGATIONS.json` 의
`{"area": "ambient failure preservation", "support": "all allocation/store/lookup/call/cleanup operation stages",
"missing": "resource/interrupt failures remain error edges; no proof yet that original result, cleanup, sealing
and return invariants survive every such edge", "new_exemption": false}`.
**16차는 그 빈자리에 구체 반례를 붙였다. 저작 레인의 과잉이 아니다.**

## ① 원본 반례의 처분 = **B · 전제의 경계를 긋는다**

**재정 문언(원리로 쓴다 · 사례로 쓰지 않는다).**

> **전제 Γ 의 경계** — 이 측정이 견뎌야 할 실패는 **프로그램이 일으킨 실패**다:
> 업무 오류 · 입출력 오류 · 계약 위반, 그리고 코드의 실행이 만들어 내는 그 밖의 모든 오류 완료.
> **실행 환경이 일으킨 실패**(해석기 자원 고갈 · 인터럽트 · 외부 신호)는 **이 측정의 오류 전제가 아니다.**
> 근거 = 그것은 산출물의 성질이 아니라 산출물을 돌리는 환경의 성질이며,
> 임의 지점의 자원 실패를 견디도록 쓰인 파이썬 산출물은 있을 수 없다.

**경계의 적용 규칙 셋.**

⑴ **프로그램이 일으킨 실패는 하나도 빼지 않는다.** 경계는 원인의 출처로만 긋고, 어려움으로 긋지 않는다.
⑵ **이 제외는 이 문언 하나뿐이다.** 다음 반례를 같은 방식으로 빼려면 **새 재정이 필요하다** — 총괄이 유추로 넓히지 않는다.
⑶ **제외는 승인이 아니다.** 검사기는 제외된 부류를 「승인」으로 세지 않고 **「이 측정의 범위 밖」**으로 표시하며,
   그 표시를 어떤 의무의 승인 근거로도 쓰지 않는다.

**이것이 후퇴라는 것을 기록에 적는다.** 12차부터 `new_exemption: false` 로 못 박아 둔 의무를 재정으로 닫는다.
정직한 후퇴가 되는 조건은 위 셋이며, 특히 ⑵ 를 어기면 그때부터는 은폐다.

**A(사실 인정)를 고르지 않은 이유** = 원본이 어기는 한 「열둘 전부 Satisfied」가 **원리적으로 불가능**해진다 —
A 단독으로는 루프가 닫히지 않고 C 와 묶여야 길이 된다.
**C(원본 수리)를 고르지 않은 이유** = 생산 9모듈 바이트 불변이 여섯 회차 근거의 축이고, 고쳐도 **모든** 자원 간선을
견디게 만들 수는 없다 — C 단독으로도 닫히지 않는다.
**D(단위 분할)를 고르지 않은 이유** = 자문 7회차가 「조건부·부분은 전체 폐쇄가 아니다」로 미리 이름 붙여 경고한 수다.

**C 가 가리킨 설계 약점은 남긴다.** 「마무리 구간이 **어느 단계의 결과인지 모른 채** 앞 단계 성공을 업무 결과로
확정한다」는 관측은 코드를 고치지 않더라도 **판단 항목 `J119` 로 등재**한다. 자원 실패를 전제에서 뺀 뒤에도
