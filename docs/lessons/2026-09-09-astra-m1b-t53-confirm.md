## ⒜ — 확인 실패는 판정자의 잘못이 아니라 발주 조건의 잘못이다

**`CONFIRM-A: 불성립`.** 게이트가 스스로 한정을 붙였다 — 「**직접 확인이 성립하지 않았다. 반례가 거짓이라는 판정은 아니다.**」

원인은 총괄의 발주 오류다. 확인 대상인 `write_closed` 는 **실제로 파일을 써야** 하는데 레인을 `read-only` 로 띄웠다. 두 줄 모두 `stages={open:Failure}` · `errno=30 Read-only file system` · `len_calls=0` 으로, **첫 단계에서 막혀 확인하려던 자리에 도달하지 못했다.** T52 확인 판은 읽기 경로였기에 같은 조건으로 성립했고, 총괄이 그 선례를 그대로 옮기며 **쓰기가 필요하다는 차이를 보지 못했다.**

**게이트가 한 일은 옳았다.** 자리는 스스로 도출했다(`t40_receipts.py:317` 의 close 완료부터 따라가 320행 `len(raw)` 가 323행 `finalize(result)` 앞에 있음을 찾고, 문자열 하위형의 `__len__` 을 달리하는 입력을 독립 작성). 방법도 「원래 있던 `len(raw)` 의 사용자 메서드 호출·오류 간선을 발동시키는 방식」으로 스스로 판정했다. 생산 9모듈의 **파일 바이트·모듈 이름 결속·355개 함수 코드 객체·중첩 명령열 동일성**을 확인했다. 그리고 코드를 읽어 「국소 슬롯에는 close 성공이 남지만 바깥 오류는 `t40_flow.py:325` 의 capture 에 보존되고 355행 unwrap 에서 재발생한다」고 적으면서 **「이는 직접 관측과 구별한다」**로 스스로 등급을 낮췄다.

**처분 = 총괄 오류 인정 · ⒜ 만 쓰기 가능한 조건에서 재실행.** 재정 T53 ② 의 「⒜ 를 부정하면 그대로 다시 상신한다」는 발동하지 않는다 — **부정이 아니라 미확인**이기 때문이다.
