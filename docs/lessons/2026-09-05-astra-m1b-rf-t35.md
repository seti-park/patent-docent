**MB-2 · HIGH — 「귀속 없음 현행 유지」의 실제 값 공간이 새 규격 밖 정의와 충돌한다**

좌표: [집행 발주문 A①](/home/laptop/projects/workspaces/pd-m1b-rf-t35/bundle/SPEC-round-rf-t35.md:15), `material_spec_md.py:477`, `D-04 §15 RF-4`.

코드 실출력:

```python
missing_attribution = any(not entry.get("reported_by") for entry in early_unclassified)
```

발주문은 현행을 「부재·빈 리스트」라고 설명하지만 실제 현행은 **`null`, `false`, `0`, `""`, `{}`도 귀속 없음**으로 처리한다. 이들은 동시에 「list가 아니므로 규격 밖」이다.

예를 들어 다음 입력은 결과를 가르는 두 지시가 충돌한다.

```json

[{"reported_by": false}, {"reported_by": ["read-a"]}]
[{"reported_by": []}, {"reported_by": ["read-c"]}]
```

첫째·둘째는 실제 현행 유지라면 귀속 없음이다. 새 규격 밖 규칙을 우선하면 규격 밖 줄이 나온다. 셋째도 「규격 밖 하나라도 있으면 줄」과 「귀속 없음 우선」의 예외 관계를 명시해야 한다.

검증 경로: A① 문언과 실제 `missing_attribution` 술어 직접 대조. 아래 형태표는 해당 술어의 정적 분석이며 렌더 실행 결과가 아니다.

수정 문안: **“우선 현행 `not entry.get('reported_by')`가 하나라도 참이면 귀속 없음만 출력한다. 아래 규격 밖·표·전건 일치 규칙은 이 조건이 거짓일 때만 적용한다.”**  
부재·`[]`만 유지하려는 의도라면, 반대로 현행 변경임을 명시해야 한다.

**사실 전제·차별 대조의 나머지 확인**

스키마 실출력:

```text
defs {"enum":["read-a","read-b"], "$comment":"...참조 밖"}
memo.read_run {"type":"string","minLength":1}
reported_by {"type":"array","items":{"$ref":"#/$defs/read_run"},
             "minItems":1,"uniqueItems":true}

```

신설 메모의 `direction: clear/concern`과 비어 있지 않은 `note`는 현재 메모 스키마와 맞는다. manifest가 가리키는 파일·스키마의 부재는 0건이다. 지정 렌더·시험 파일과 T32 선례 `794c639`도 존재한다.

실런 조회 결과:

| 런 | early의 reported_by 목록 | full의 reported_by 목록 | 두 파일의 메모 실행값 |
|---|---|---|---|
| gdm-agent-memory | `[]` | `[]` | 각각 `read-a`, `read-b` |
| cim-fp-2 | `[]` | `[]` | 각각 `read-a`, `read-b` |
| cim-fp-3 | `[]` | 키 부재 1항목 | 각각 `read-a`, `read-b` |

총 6파일이다. 여기서 `[]`는 미분류 항목 자체가 없다는 뜻이다. **전체 문서의 validator 통과 여부는 실행 금지 때문에 재측정하지 않았다.** cim-fp-3의 두 required 위반 원인은 실물로 확인했다.

| 대조 | 태우려는 코드 조건 | 설계 판단 |
|---|---|---|
| Aⓐ | 허용 실행값 소속 검사 | 목적 타당. 두 조건을 각각 제거해 각 케이스가 잡는지도 분리하면 관할이 명확해진다 |
| Aⓑ | 규격 밖 항목만 세는 N | `[a,b]+[c]`에서 1 대 2로 구별 가능 |
| Aⓒ | 두 값의 서로 다름 | `[a,a]`가 판별 입력 |
| Aⓓ | 규격 밖과 정상 singleton의 동시 출력 | 존재 여부 판별 가능. 순서는 MB-6 |
| H | T22 `action=="escalate"` 등 | 기존 단언의 관할 재현. 주석 변경 차별은 불가능 |
| B⑴ | 메모 read_run의 `$ref` enum 결속 | 구 자유 문자열에서 `read-c` 허용, 새 enum에서 거부라는 설계 타당 |
| B⑵ | reported_by `maxItems` | 확장 enum 사본이면 독립 판별 가능 |
| B③ | 세 참조와 정의 결속 | 구조 계약 확인. B⑴의 행위 대조가 별도로 있어 형상만 남지 않음 |

현재 enum 둘로 길이 3을 만들면, 허용값만 쓸 경우 반드시 중복이고 서로 다르게 만들면 enum 밖 값이 필요하다. 따라서 **현재 enum에서 `maxItems`만 위반하는 길이 3 픽스처는 불가능**하다. 확장 enum 방식은 옳다. 다만 `maxItems` 위반이 있다는 확인과 함께 다른 위반이 없다는 것도 명시하면 판별이 더 분명하다.

참조 셋 변경은 기존 시험에서 다음을 함께 바꿔야 한다.

- `expected_definition`의 `$comment` 정확 일치값.
- `len(refs) != 2` 단언과 메시지.
- 메모 read_run이 `{type:string,minLength:1}`이어야 한다는 마지막 역방향 단언.
- 새 메모 `$ref` 확인 및 함수명.

**reported_by 형태표 — 정적 분석**

`a=read-a`, `b=read-b`, `c=read-c`. G=귀속 없음, I=규격 밖 줄, T=표, A=전건 일치. MB-2의 우선 규칙을 명확히 했다고 가정한 기대다.

| 형태 | 기대 | A의 명시 상태 |
|---|---|---|
| `[a,b,c]` | I(1) | 명시 |
| `"read-a"` | I(1) | 정의·기존 시험 |
| `5` | I(1) | 정의로 도출 |
| `{"read-a":1}` | I(1) | 정의로 도출 |

| 길이 3 두 항목 | I(2) | 명시 |

전임 표는 제목이 「17종」이지만, 표시된 개별 입력을 풀어 세면 **16개**다. 없는 17번째 입력을 만들어 실측했다고 하지 않았다.
