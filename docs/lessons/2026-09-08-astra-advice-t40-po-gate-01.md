# 외부 자문 답변 --- PO-GATE-01 만족 가능성과 해결 방향

## 결론

**\[추정·종합 판정\] PO-GATE-01은 원리적으로 만족 가능하다.** 요구를
"모든 Python 프로그램의 안전 여부를 완전하게 판정한다"가 아니라
**"검사기가 PASS시킨 코드에서는 기존 불변식이 실제로 강제된다"**로 읽는
것이 타당하다.

최근 심사자는 "미구현 조합은 위치 있는 Unsupported로 거부"하도록
요구했다. 따라서 의미를 보증하지 못한 코드를 사전에 비승인하는 것은
허용되지만, PASS시킨 뒤 반례가 나오자 "그 의미는 미지원이었다"고 사후
제외하는 것은 허용되지 않는다.

현재의 **"등록하지 않은 것은 거부한다"**는 방향은 유지하는 것이 맞다.
바꿔야 하는 것은 "지원"의 기준이다. AST 타입·필드 등록이나 evaluator
존재만으로 지원을 선언하지 말고, **관련 정상·오류 완료, 효과 순서, 후속
실행 여부까지 건전하게 모델링되었을 때만 지원으로 승인**해야 한다.

## Q1. 읽기와 만족 가능성

필요한 보증은 다음 방향이다.

``` text
G(p) = PASS  =>  p satisfies the existing invariants
```

모든 안전한 Python 프로그램을 반드시 PASS해야 하는 것은 아니다. 의미를
보증할 수 없는 조합은 `Unsupported`로 거부할 수 있다.

다만 "전부 거부"도 해법이 아니다. 실제 제출 원본과 기존 필수 양성 사례는
계속 승인되어야 한다. 즉 **승인한 코드에는 위반이 없다는 근거**와 **실제
필요한 코드는 승인할 수 있다는 근거**를 동시에 확보해야 한다.

**\[미확인·일반 이론\]** 모든 임의 프로그램을 항상 정확히 판정하는
완전한 일반 판정기는 결정불가능성의 제약을 받는다. 그러나 확인하지 못한
코드를 거부하는 건전한 승인기까지 불가능한 것은 아니다.

## Q2. 의미 층에도 기본 거부를 적용할 수 있는가?

**가능하다.** 원칙은 다음이다.

> 승인에 필요한 의미 보증이 없으면 승인하지 않는다.

최근 반례:

``` python
{**(), 0: machine.finalize(result)}
```

실제 흐름:

``` text
() 평가
→ ** 병합 시도
→ TypeError
→ 뒤의 machine.finalize(result)는 실행되지 않음
```

기존 모델은 피연산자 평가와 병합 연산 자체를 분리하지 않아 이 오류
완료를 빠뜨렸다. 공통 의미 규칙은 다음 형태가 되어야 한다.

``` text
입력 평가
    ├─ 오류 완료 → 오류와 현재 상태 전달
    └─ 정상 완료 → 연산 수행
                     ├─ 오류 완료 → 뒤 동작 실행 금지
                     └─ 정상 완료 → 다음 동작
```

핵심은 반례별 예외 목록을 늘리는 것이 아니라 **각 지원 규칙의 건전성과
규칙 합성의 건전성을 근거로 승인하는 것**이다.

## Q3. 다른 구조

### A. 현재 구조를 유지하되 승인기를 건전하게 만든다

1.  지원 구문의 의미 계약을 명시한다.
2.  정상 완료와 오류 완료를 같은 합성 체계에서 다룬다.
3.  각 연산의 실패 전후 효과를 모델링한다.
4.  의미 계약이 없는 조합은 `Unsupported`로 비승인한다.
5.  원본과 기존 필수 양성이 계속 승인되는지 확인한다.

구체적인 실행 예제는 별첨 `PO_GATE_01_examples_FINAL.zip`에 제공한다.

### B. "증명을 찾는 검사기"에서 "제시된 증명을 확인하는 검사기"로 이동한다

``` text
산출물에 대한 증명 확보
→ 증명과 실제 산출물의 일치 확인
→ 증명 검증
→ 검증된 산출물만 실행 승인
```

한 줄 변경은 기존 증명과 맞지 않으므로 재인증 없이는 승인되지 않는다.
대가는 변경 자유도의 감소다. 해시나 바이트 동일성만으로는 안전성 증명이
되지 않으므로 원본의 안전성 근거와 검증기의 신뢰 근거도 필요하다.

### C. 위반 가능한 자유도를 구조적으로 줄인다

장기적으로는 변경 가능한 부분을 선언적 명령으로 제한하고 작은 검증된
실행 핵심부만 결과 확정·cleanup·seal·공개 권한을 소유하도록 만들 수
있다. 다만 현재 제약상 측정 대상 러너 62파일은 변경 금지이므로, 러너
변경이 필요한 구조는 이번 판의 직접 해결책으로 사용할 수 없다.

## Q4. PO-GATE-01 재작성 예

> **PO-GATE-01 --- 누락·통로 밖 경로에 대한 정적 승인 건전성 및 기존
> 의무 연속성**
>
> 기존 성질과 전제를 변경하지 않는다. 정적 검사기가 생산 산출물을 승인한
> 경우, 그 산출물에서는 이 의무에 연결된 기존 성질이 강제되고 기존
> 의무의 연속성이 유지됨을 보증한다.
>
> 승인은 실제 실행의 관련 정상·오류 경로와 효과 순서를 빠뜨리지 않는
> 의미 모델 및 그 합성 근거, 또는 해당 산출물에 결부된 검증 가능한
> 증명에 근거한다. 지원 등록, evaluator 존재, 구문 순회 완료, 시험 통과
> 수만으로 승인을 정당화하지 않는다.
>
> 미지원 구문·조합, 확인되지 않은 지원 전제, 미해결 증명, 검사 실패는
> 비승인으로 처리한다. 미지원은 해당 코드의 승인을 거부하는 사유이며,
> 이미 승인한 코드의 반례를 면책하는 사유가 아니다.
>
> 실제 제출 원본과 기존에 승인이 요구된 양성 사례는 기존 요구를 유지한
> 채 승인되어야 한다. 이를 증명하지 못하면 이 의무는 닫히지 않는다.

이것은 기존 안전 목적을 약화시키는 후퇴라기보다 승인 조건을 명료화하는
것이다.

## Q5. 수렴 판별

어김 수가 1로 고정됐다는 사실만으로 수렴을 증명할 수 없다. 핵심 관측은
다음이다.

> 모델이 보증하지 않는 조합이 승인 경계에서 거부되는가, 아니면
> 지원한다고 승인한 뒤 실제 성질이 깨지는가?

수렴 관리는 다음 세 값을 분리하는 것이 좋다.

``` text
U_r = 승인 근거 중 건전성·합성 근거가 아직 해결되지 않은 항목 수
B_r = 반드시 승인해야 하는 원본·양성군 중 비승인된 항목 수
L_r = 독립 검증에서 발견된 “성질을 깨뜨리면서 승인된” 사례 수
```

목표는 `U_r → 0`, `B_r = 0`, `L_r = 0`이다. `U_r`의 목록은 현재 검사기
구현이 아니라 독립적인 기준 의미와 기존 불변식에서 도출해야 한다.

## Q6. 세 회차 안의 실패 신호

### 41회차 --- 승인 경계

보증되지 않은 변경은 비승인되고, 원본과 필수 양성은 계속 승인되는지
본다.

### 42회차 --- 의미 계약과 합성

한 지원 범주를 골라 개별 반례 목록이 아니라 **의미 계약 + 정상/오류
완료 + 합성 근거**를 제출한다. 이 범위에서 다시 실제 실패 경로가 승인된
채 발견되면 접근이 아직 구현되지 않은 것이다.

### 43회차 --- 수렴 구조

동일한 성질과 전제를 유지하면서 독립 증명 항목의 미해결 수가 감소하고
원본·필수 양성·변경 금지 조건이 유지되는지 본다.

세 회차 동안 반례가 없다는 사실만으로 지킴을 선언해서는 안 된다.
**승인을 정당화하는 독립적 근거가 생겼고 미해결 근거가 실제로 줄고
있는가**가 판별 기준이다.

## 코드 저작자에게 보여 줄 핵심 예

### 예 1 --- 최근 반례를 문자열 차단하지 않는다

``` python
machine.finalize(result)
{**(), 0: machine.finalize(result)}
{**{}, 0: machine.finalize(result)}
```

`()`라는 특정 모양을 금지하는 것이 아니라 **피연산자 평가와 병합 연산을
분리하고, 병합이 오류 완료되면 뒤 항목으로 진행하지 않는 공통 의미
규칙**을 구현해야 한다.

### 예 2 --- 오류 완료를 공통 합성 규칙으로 전달한다

``` python
if outcome.flow is NORMAL:
    continue_with_next(outcome.state)
else:
    propagate(outcome)
```

정상 완료했을 때만 다음 동작을 실행한다. 실제 검사기가 더 많은 제어
이동을 지원한다면 그 지원 범위에 맞는 완료 종류와 합성 규칙을 별도로
증명해야 한다.

### 예 3 --- finalize 실행 여부만으로 충분하지 않다

``` python
{0: machine.finalize(result), **()}
```

`finalize`는 실행되어도 이후 병합 실패로 cleanup·seal·원래 결과 반환이
생략될 수 있다. 따라서 관련 완료 경로 전체에서 기존 불변식이 유지되는지
확인해야 한다.

### 예 4 --- finally만으로 전체 의무가 자동 복구되지는 않는다

``` python
try:
    {**(), 0: 1}
finally:
    machine.finalize(result)
    machine.cleanup()
    machine.seal()

return result
```

정리 동작이 실행되어도 예외 재전파 때문에 원래 업무 결과 보존 요구가
깨질 수 있다. cleanup 보장과 결과 보존은 별도로 검증해야 한다.

## 코드 저작자용 적용 순서

1.  최근 `Dict` 반례를 특수 패치하지 않는다.
2.  현재 "지원" 규칙의 의미 계약을 작성한다.
3.  피연산자 평가와 연산 자체의 실패를 분리한다.
4.  정상·오류 완료와 효과 상태를 공통 합성 규칙으로 연결한다.
5.  의미 계약이 없는 조합은 승인하지 않는다.
6.  원본과 기존 필수 양성이 계속 승인되는지 확인한다.
7.  기존 8개 불변식과 12개 PO를 늘리거나 약화하지 않는다.
8.  변경 금지 러너 62파일과 바이트 동일 유지 대상을 수정하지 않는다.
9.  독립 기준에서 도출한 증명 항목의 미해결 수를 관리한다.
10. 다시 "지원한다고 승인했지만 실제 실패 의미가 빠진" 반례가 나오면
    개별 패치보다 상위 의미 계약의 건전성을 재검토한다.
